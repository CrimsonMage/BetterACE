# bace-dat-service

Bounded DAT-distribution foundation: immutable metadata catalogs, interrogation and iteration comparison, Begin/Data/End planning, portable zlib preparation, and permitted on-demand Cell requests. Disabled by default when composed by runtime. This does not independently enable DAT distribution on the host.

`DddCatalog` receives validated database iteration/record metadata from asset preparation; required Portal/Language metadata must exist. It keeps records sorted by ID and one index per iteration. Planning work scales with declared server iterations plus records in missing iterations, rather than scanning every record once per iteration. Default engineering budgets are 100,000 iterations, five million catalog records, 16,384 pending records, 256 MiB per transfer, and 256 KiB Begin messages. `DddLimits::stock_patch()` is the opt-in larger bound: 16 MiB per DAT record, 4 MiB Begin, one million planned files and 2 GiB transfer. Its 16 MiB record bound requires the network adapter to accept a 16 MiB plus 33-byte DDD Data message and reserve that much outgoing capacity. These are engineering limits, not claims about every proprietary DAT.

`DddCatalog::from_archive_indexes` reads the ACE version record `0xFFFF0001` from each fingerprint-admitted archive and publishes only database iterations. It is for the default patch-disabled path, where an up-to-date client receives End and an outdated client is rejected without a costly record scan. Enabled sessions reject this index-only catalog. `DddCatalog::from_archives` runs on blocking asset-preparation capacity, derives source resource types, and computes exact Portal/Language/HighRes transfer sizes by reading and compressing each record. Cell metadata uses indexed raw sizes, so 805,000+ Cell records are not read at startup. On-demand Cell jobs must use `prepare_archive_record_uncompressed` to match that metadata; other jobs use `prepare_archive_record`. Sending valid raw Cell payloads with the compressed flag clear is a deliberate CPU policy deviation from ACE, which may zlib-compress Cell files. Both catalog constructors depend on the caller's prior DAT fingerprint admission.

`DddSession` owns one bounded transfer queue and at most one in-flight asset job. `begin` atomically compares the client's bounded iteration runs, rejects newer clients and missing required databases, returns End for up-to-date clients, and returns Begin plus queued preparation work for enabled patching. Cell iteration entries are listed but their records are downloaded on demand and omitted from initial transfer bytes, matching ACE. HighRes/Cell zero iteration sets do not request initial patching. Failed preparation retains its job; generation and record metadata checks reject stale/mismatched results. End is acknowledged only after queued work is handed to reliable output; it is not evidence that the client persisted its DAT.

`prepare_archive_record` is a **blocking asset-worker** entry point over a verified `DatArchive`. It bounds record size before reading, uses validated resource-type metadata, and produces a `PreparedRecord`. Runtime must execute it on separate bounded asset-preparation capacity, never simulation or the network thread. `prepare_record` applies ACE's selection policy: use zlib only when compressed length plus the four-byte original-length prefix is smaller than raw length. Its compressor has a fixed output limit; incompressible data remains raw. Exact compressed bitstream equality with .NET is not claimed. Prepared size metadata must be computed off-thread before catalog publication; mismatches abort completion rather than silently changing the Begin transfer plan.

On-demand requests require an externally verified WorldConnected session and a completed DDD negotiation. Only LandBlock (1), LandBlockInfo (2), and EnvCell (3) are accepted. A LandBlock includes its preceding LandBlockInfo when present. Unsupported types, absent records, disabled patching, capacity failures and stale results return explicit `DddError` values. The session adapter maps these to policy/error messages using `bace-wire::DddControl::Error`; it must not fabricate a successful download. Output produced by `complete_job` must enter bounded reliable output or remain retained by the caller.

Source provenance: official ACE at `47edade3bd3f6044b676d4eb877c4965c7eda62b`, [DDDHandler.cs](https://github.com/ACEmulator/ACE/blob/47edade3bd3f6044b676d4eb877c4965c7eda62b/Source/ACE.Server/Network/Handlers/DDDHandler.cs), [DDDManager.cs](https://github.com/ACEmulator/ACE/blob/47edade3bd3f6044b676d4eb877c4965c7eda62b/Source/ACE.Server/Managers/DDDManager.cs), `GameMessageDDDDataMessage.cs`, and `ACE.DatLoader/DatFileType.cs`. AGPL-3.0-only. Wire message layouts have compiled official C# vectors in `bace-compat`; service planning tests are behavioral evidence, not full differential DDD-handler parity.

Intentional hardening: strict unique iteration membership rejects malformed/duplicate runs and missing required database reports. ACE's `GetMissingIterationsFromClient` shortcut treats any run whose absolute value equals the server maximum as complete; BACE requires actual coverage, so reporting only the final iteration cannot fabricate possession of every earlier one. Absent server records never produce empty successful DDD data messages.

Validation: `cargo test -p bace-dat-service` covers disabled/newer clients, bounded/atomic plans, malformed run handling, stale completions, retry retention, on-demand companions and compression thresholds. Run `cargo test -p bace-dat-service --test zlib_oracle -- --ignored` for an independent Python/system-zlib decode of the Rust-compressed payloads. This suite requires Python and is not an automatic pass when unavailable.

The configured local DATs were checked read only: Portal has 79,694 records (852,004,981 raw bytes; largest 8,949,784), Language has 118 (700,113 raw bytes), and Cell has 805,348 (210,460,134 raw bytes; largest 19,728). The Portal+Language raw transfer upper bound is below the 2 GiB opt-in limit, and all transferable IDs classify under pinned ACE's `DatFile.GetFileType` mapping. These observations are machine-local asset evidence, not shipped proprietary fixtures or a stock-client transfer result.

Remaining integration gates: runtime asset-worker and network-capacity wiring, complete official DDD-handler differential replay, real DAT/client transfer traces and Windows/macOS validation. The service alone is not a claim of working production DAT patching.
