# Physics arithmetic and SIMD qualification

Status: decision and future acceptance gates. The current implementation is a synthetic sphere/box harness. No AC collision oracle, retail-client reconciliation, SIMD speedup, or x87 equivalence has been demonstrated.

One dedicated simulation thread owns world mutation and physics. SIMD may eventually batch independent arithmetic **inside that thread**; it does not authorize parallel ownership, reordered contact resolution, or worker threads mutating bodies. Geometry/assets and inputs are immutable during a tick. See [SIM-01 through SIM-05](../ARCHITECTURE.md#simulation-and-authority).

## Reference and decision

The official ACE pin uses `System.Numerics.Vector3` for velocity/acceleration, `float` physical coefficients, and `double` update timestamps. The comment `long double?` on `CallPES` is not an executable precision specification. See pinned [PhysicsObj.cs](https://github.com/ACEmulator/ACE/blob/47edade3bd3f6044b676d4eb877c4965c7eda62b/Source/ACE.Server/Physics/PhysicsObj.cs#L56-L86) and [CallPES](https://github.com/ACEmulator/ACE/blob/47edade3bd3f6044b676d4eb877c4965c7eda62b/Source/ACE.Server/Physics/PhysicsObj.cs#L277-L287). Microsoft documents `Vector3` as three single-precision components with hardware-dependent SIMD acceleration. This source therefore does not establish an x87-only server baseline. [Microsoft SIMD documentation](https://learn.microsoft.com/en-us/dotnet/standard/simd#systemnumerics-vector-and-matrix-types).

x87 extended precision and binary32/binary64 are distinct formats. Replacing an extended intermediate with a narrower operation can change a boundary decision; SIMD alone does not reproduce extended precision. [Intel floating-point reference](https://www.intel.com/content/www/us/en/developer/articles/technical/floating-point-reference-sheet-for-intel-architecture.html). Which instructions and rounding modes the supported retail client actually uses remains an empirical client/oracle question. Do not infer them from its age or from a decompiler's type annotation.

**MATH-01:** Port each upstream expression with its documented storage width, operation order, casts and thresholds first. Keep explicit `f32` geometry and `f64` where the reference uses double; a wholesale switch to `f64`, fixed point, or emulated x87 is prohibited without differential evidence. Do not add a SIMD dependency solely to replace the present three-component scalar type.

**MATH-02:** Optimizations MUST preserve validation of finite inputs, contact ordering and classification. Do not introduce fast-math, approximate reciprocal/square-root, reassociated reductions, or fused multiply-add as incidental cleanup. Each changes the numerical contract and requires separate qualification. Rust documents primitive float rounding and distinguishes fused `mul_add` from separately rounded operations. [Rust f32 documentation](https://doc.rust-lang.org/std/primitive.f32.html#method.mul_add).

**MATH-03:** Keep a scalar reference path for comparisons. First inspect optimized code and profile realistic data: compiler vectorization may already remove the proposed bottleneck. If explicit SIMD proves useful, prefer a safe stable API with scalar fallback, fixed and tested lane ordering, and no changes to serialized layouts. As checked on 2026-10-07, `std::simd` is experimental/nightly-only; that is not a reason to change this workspace's stable toolchain. [Rust portable SIMD documentation](https://doc.rust-lang.org/std/simd/index.html).

## Accuracy gates before enabling an optimized path

These are project acceptance requirements, not measured results or client tolerance claims.

1. Record the upstream commit, .NET runtime/JIT, Rust compiler, target CPU/features, build flags, floating-point mode, DAT hashes, and deterministic input seed with every comparison. Preserve a scalar fixture set and separately label oracle-derived fixtures. No proprietary DATs or player captures are committed.
2. Differential-test at least 1,000,000 seeded primitive cases plus explicit adjacent-representable values at every predicate boundary: positive/negative zero, subnormal deltas, tangent faces/edges/corners, nearly parallel sweeps, degenerate inputs, large supported coordinates, floor/slope thresholds, and maximum legal speeds. Nonfinite inputs must be rejected before state mutation. Compare hit/miss, selected cell/face, contact order, rejection reason, and all numerical outputs.
3. An initial SIMD implementation MUST match scalar finite outputs bit-for-bit and discrete decisions exactly. If the useful implementation cannot do that, stop its rollout and propose a separate, justified per-operation ULP/absolute-error budget. Never accept a global epsilon that hides changed collision branches. ACE's `EPSILON = 0.0002f` is a particular source constant, not a blanket allowable trajectory error. [Pinned PhysicsGlobals.cs](https://github.com/ACEmulator/ACE/blob/47edade3bd3f6044b676d4eb877c4965c7eda62b/Source/ACE.Server/Physics/PhysicsGlobals.cs).
4. Replay at least 18,000 ticks (ten minutes at 30 Hz) with repeat runs producing identical same-build state hashes. Compare scalar and candidate state, contact and event streams at every tick. Include high-speed thin-wall tests, jump/landing, opposing motion, start/stop, missing release reports, teleport epochs and multiple actors. Authentic terrain/BSP, dungeon transitions and portals require additional validated DAT and pinned ACE/stock-client traces before an AC compatibility claim.
5. Stock-client acceptance additionally requires two clients traversing outdoor/dungeon geometry and portals without unexplained corrections or authority violations. Any approved numerical difference must identify the earliest divergent operation and show that valid behavior and collision decisions remain acceptable. Synthetic replay success cannot waive this gate. Cross-platform bitwise determinism remains unpromised; every supported target must pass its own suite.

## Performance gates

Profile the scalar baseline first. A candidate requires a measured kernel accounting for at least 10% of physics time on the target workload. Benchmark scalar and candidate with identical datasets, compiler/profile/CPU settings and warm-up; include lane tails, small batches and conversion/allocation costs. Run at least five independent repetitions and report median, range and p95/p99 tick times, CPU time and peak memory. Accept only an improvement of at least 10% in kernel median and 5% in whole-tick median, with no p99 regression exceeding 2%; these are adoption thresholds, not promises.

The overall gate remains 100 moving synthetic players and 1,000 additional physics bodies for ten minutes, p99 tick computation at most 25 ms, no sustained missed 30 Hz deadlines, and injected 500 ms database latency unable to stall the owner. The same corpus must pass accuracy gates before timing counts. Record hardware, OS, governor, dataset and build so results are reproducible. A SIMD microbenchmark cannot establish server capacity, and DB concurrency must not add simulation owners.

## Current correctness regressions

The synthetic AABB sweep uses the **open interior** of expanded slabs: tangent motion away from or parallel to a face is permitted, while inward motion is blocked at time zero. A zero-duration corner touch does not imply penetration. Exact zero deltas receive the stationary-axis path; small nonzero deltas are still evaluated. This is a conservative expanded-box sphere approximation, not an AC narrow-phase port.

`World::insert` validates the body's accepted position and radius against its destination scene before taking ownership. A body valid in one scene cannot bypass another scene's obstacle/floor checks; failed insertion and teleport leave the world unchanged. Coverage lives in [geometry sweep tests](../crates/foundation/bace-geometry/tests/sweep.rs), [physics authority tests](../crates/simulation/bace-physics/tests/authority.rs), and [world placement tests](../crates/simulation/bace-world/tests/placement.rs).
